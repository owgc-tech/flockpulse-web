DIP-FP-55-FP-75-FP-88 — Registrant Completes Registration (Demographics, Locked Role/Group)
Covers: FP-55 (Registrant Completes Registration via Invitation), FP-75 (Add Demographic Fields to Members — gender, marital_status), FP-88 (Add Birthdate to Members) Epic: FP-8 (EPIC-2 — Member & Group Management)
Story Summary
The invited person (FP-54) clicks their email link, sets a password, then completes a registration screen: name, gender, marital status, and birthdate — all self-reported, all required. Role and group are displayed read-only, sourced from the invitation the Admin already created — the registrant never sees them as choices, at this step or any later one.
This is the first time in this codebase that a genuinely new, non-privileged user's own JWT is used to create a `members` row. Every prior write path this session either used the service-role client or operated on an already-established member acting on their own existing record. Treat the authorization mechanism here — proving the caller is the exact person a `PENDING` invitation was issued to — as the single most security-critical piece of this DIP.
FP-75 and FP-88 are folded in because they are literally fields on this same screen, not separable work — building FP-55 without them means building this screen twice.

6. `app_metadata.member_id` must be set after registration completes — this cannot happen inside the SQL function. Confirmed by checking FP-54's own `getAdminContext` pattern (`app/admin/invite/actions.ts`), which already expects `member_id` to be present in `app_metadata` for context resolution. Writing to `app_metadata` requires the Admin API (`updateUserById`), which needs the service-role key — the registrant's own client never has this. This means completion is a two-step application-layer process, same shape as FP-54's own two-step Auth pattern: (1) call `complete_registration()` using a client authenticated with the registrant's own access token (so `auth.uid()` resolves correctly inside the function); (2) immediately after success, using the service-role client, call `updateUserById` to add `member_id` to that same user's `app_metadata`.

This held true locally (migrations run before seed.sql, so `members` is always empty at migration time). The migration was amended to add the columns nullable first, then backfill with placeholder values (`'MALE'`, `'SINGLE'`, `'1990-01-01'` — matching the convention in seed.sql), then apply `NOT NULL`. Grounding note for future schema additions: always include a backfill step when adding `NOT NULL` columns to a table that may have rows in any environment, even if the local reset path is clean.

2. `complete_registration()` — draft, confirm shape against real `assignments` schema before finalizing:

```sql
CREATE OR REPLACE FUNCTION public.complete_registration(
    p_first_name TEXT,
    p_last_name TEXT,
    p_gender TEXT,
    p_marital_status TEXT,
    p_birthdate DATE
)
RETURNS TABLE (member_id UUID, tenant_id UUID, role TEXT, group_id UUID)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_catalog
AS $$
DECLARE
  v_invitation invitations%ROWTYPE;
  v_member_id UUID;
BEGIN
  SELECT * INTO v_invitation
  FROM invitations
  WHERE auth_user_id = auth.uid() AND status = 'PENDING'
  FOR UPDATE;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'No pending invitation found for this account';
  END IF;

  INSERT INTO members (tenant_id, user_id, email, first_name, last_name, role, gender, marital_status, birthdate)
  VALUES (v_invitation.tenant_id, auth.uid(), v_invitation.email, p_first_name, p_last_name,
          v_invitation.role, p_gender, p_marital_status, p_birthdate)
  RETURNING id INTO v_member_id;

  IF v_invitation.group_id IS NOT NULL THEN
    INSERT INTO assignments (tenant_id, member_id, group_id, assignment_type)
    VALUES (v_invitation.tenant_id, v_member_id, v_invitation.group_id, 'GROUP');
  END IF;

  UPDATE invitations
  SET status = 'ACCEPTED', responded_at = now()
  WHERE id = v_invitation.id;

  PERFORM write_audit_log(v_invitation.tenant_id, 'member', v_member_id, 'register',
    v_member_id, NULL, to_jsonb((SELECT m FROM members m WHERE m.id = v_member_id)));

  RETURN QUERY SELECT v_member_id, v_invitation.tenant_id, v_invitation.role, v_invitation.group_id;
END;
$$;

```

3. Set-Password screen (first step): calls `supabase.auth.updateUser({ password })` using the session already established by the invite link.
4. Complete-Profile screen (second step): first/last name inputs, Gender dropdown, Marital Status dropdown, Birthdate input — all required. Role and Group displayed read-only, sourced from the caller's own `app_metadata` (already present since FP-54's invite-time stash) — group name may need a light read-only lookup if only `group_id` is available client-side.
5. Submit handler, two-step (per Grounding Check item 6):
   * Call `complete_registration()` via a client authenticated with the registrant's own access token.
   * On success, using the service-role client, call `updateUserById(authUserId, { ...existing, member_id: returnedMemberId })`.
   * On success: static confirmation text ("check your email / download the app") — no new send-logic.
   * If `complete_registration()` raises (no matching `PENDING` invitation), show a clear error — do not silently redirect or retry.
6. Regression check: confirm no existing test script or route assumes `members` has exactly the prior column set — anything doing `SELECT *` or explicit column lists against `members` should still work with three new `NOT NULL` columns added, but confirm rather than assume.
